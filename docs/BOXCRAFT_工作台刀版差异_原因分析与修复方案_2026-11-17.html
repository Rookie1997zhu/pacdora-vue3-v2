工作台刀版与 Pacdora 差别大：原因分析与修复方案

范围：http://localhost/workbench 里从 Pacdora 采集来的折叠盒与托盘盒。结论基于对全部 583 个采集盒型的逐一比对，以及对线上页面的实际查看。本次只读代码和数据，没有改动任何文件。

1结论

差别大的主要原因不是参数没调准，而是画的根本不是同一个盒子结构。工作台对采集来的盒型只用了三个数：长、宽、高。结构本身是按盒子名称里的关键词挑一个我们自己的通用模板来画的，Pacdora 那份完整刀版（面片、切线、折线、孔、结构参数）在工作台里完全没有被用到。

结构对不上（主因）

折叠盒有 360 种 Pacdora 结构，被挂到 21 个通用模板上，其中 139 个都挂在同一个“直插舌盒”上。已挂模板的盒型里，面片数量与 Pacdora 相同的只有 64 / 302（折叠盒）和 4 / 115（托盘盒）。

已有的精确模板没接上

项目里本来有按 Pacdora 结构代码对应的参数化模板和“结构规格编译器”，但折叠盒、托盘盒的结构代码没有回填，这条链路整段被跳过。53 个盒型本可直接用上精确模板。

结构参数和轮廓细节全丢

Pacdora 折叠盒每个平均有 13 个结构参数，工作台传进引擎的是空对象。通用模板的面片全是矩形，而 Pacdora 93% 的折叠盒带圆弧；带孔的盒型 Pacdora 有 254 个，我们画出来只有 76 个。

另有两个显示缺陷

出血线被画成一个大圆；刀版缩在画板左下角很小一块。这两个与数据无关，是代码缺陷，会让任何盒型看起来都不对。

一句话的修法。先修两个显示缺陷；再把已有的“结构代码 → 精确模板”和“结构规格编译”两条链路接到折叠盒与托盘盒上；最后给每个盒型算一个与 Pacdora 的吻合度分数，达标的才标为“可定制”，不达标的改为尺寸锁定展示或暂不提供。

3八个原因（按影响从大到小）

原因 1：用名称关键词挑模板，结构不是同一个 主因

  • 位置：scripts/build-presets-from-csv.mjs 的 mapTemplate(name, mockup, num)，用正则在英文和中文名称里找 tuck / handle / pizza / hang / zipper… 等词，返回一个通用模板 id。
  • 后果：名称只能说明盒子的大类，说明不了结构。360 种结构被归到 21 个模板，同一个模板要代表几十种不同的锁扣、插舌、内衬结构。
  • 证据：第 2 节的面片数量、展开尺寸、切线长度三项数据。

原因 2：结构代码没有回填，精确模板和规格编译整段被跳过 可立即修

项目里已有两套能做到“按 Pacdora 结构生成”的机制，但都没有作用到折叠盒和托盘盒：

原因 3：Pacdora 的结构参数没有传进引擎 主因

  • 位置：src/features/workbench/manifest.ts 的 manifestFromImportPreset()，defaultParams.advanced 固定为 {}。
  • 后果：采集到的 openParams（插舌长、防尘翼高、糊口宽、倒角半径等，折叠盒中位数 13 个）全部没用。已挂模板的 417 个盒型里，413 个用的模板根本没有 paramDefs，工作台的“高级”页签是空的。
  • 预设里也没有保存 openParams，只保存了 cutCount / foldCount / sheetW / sheetH 这几个统计值。

原因 4：通用模板只有矩形面，没有圆弧、斜边和孔 主因

  • 折叠盒和托盘盒用到的 16 个手写通用模板（tuck-end-straight、hanging-tuck、handle-box、drawer-tray、display-pdq、pizza-clamshell 等），面片全部是矩形，没有一个带多边形轮廓。
  • Pacdora 的插舌是圆角，防尘翼有斜边和让位缺口，糊口有斜角，提手和挂孔是异形孔。这些正是“看起来像不像”的关键。
  • 只有 spec-* 和 rea-* 两类模板有多边形轮廓，而它们只覆盖了 10 个折叠盒。

原因 5：尺寸补偿规则与 Pacdora 不同 次因

预设里的长宽高取的是 Pacdora 的内尺寸（456 / 459 吻合），工作台也按内尺寸输入，这一步没错。但从内尺寸推制造尺寸的加量不同：

材质厚度Pacdora 最常见的加量（长 / 宽 / 高）我们的加量
0.5mm 卡纸+0.6 / +0.6 / +1.1（91 个）；也有 +0.6 / +0.6 / +0.6、+0.6 / +0.6 / +1.6 等，因结构而异插舌类模板 +0.5 / +0.5 / +1.0；托盘类 +1.0 / +1.0 / +0.5

这一项造成的偏差在 0.1–1.5mm，肉眼看不出，但会让所有标注数字与 Pacdora 对不上。Pacdora 的加量是按结构定的（每个盒型的 getKnifeSizeAdd 不同），不是一条全局规则。

原因 6：出血线被画成圆 代码缺陷

  • 现象：页面上出血线是一个包住刀版的大绿圈。实际路径为 M 12 12 A 162.373 162.373 0 1 1 12 252.63 Z。
  • 位置：src/geom/flattenPath.js 的 arcRun()，被 pathCommandsFromLoop() 调用。它用“连续 4 个点是否共圆、转角是否均匀”来判断一段折线是不是圆弧。
  • 根因：矩形的 4 个角天然共圆，转角都是 90°。所以任何 4 点矩形环都会被识别成一段 270° 的圆弧。矩形模板的出血线正好是外接矩形，于是变成圆。已用 pathCommandsFromLoop([[12,12],[230,12],[230,252],[12,252]]) 复现。
  • 影响范围：所有出血为外接矩形的模板；切线里如果出现 4 个共圆且转角均匀的顶点（正方形孔、正多边形面）也会中招，导出文件同样受影响。

原因 7：刀版缩在画板角落 代码缺陷

  • 现象：画板 759 × 320 像素，刀版只占左下角约 60 像素，缩放比例是 0.265。
  • 位置：src/features/workbench/components/canvas/DielineCanvas.vue 与 composables/useViewport.ts。
  • 根因：fit() 只在第一份刀版到达后的 nextTick 调用一次，此时容器尺寸还没稳定，按很小的宽高算出了缩放；之后的判断条件是 scale === 1 && tx === 0，已经不成立，不会再适应。没有监听容器尺寸变化。画板高度固定在最小 320 像素左右，也没有撑满可用空间。

原因 8：数据本身的限制

  • 几乎一盒一结构。按面片名称集合统计，459 个折叠盒有 356 种不同拓扑，前 20 种只覆盖 22%；124 个托盘盒有 110 种。靠手写模板逐个覆盖不现实。
  • 每种结构只有一个尺寸的样本。只知道它在默认尺寸下长什么样，不知道改尺寸后各个面怎么变。任何“可改尺寸”的生成都只能靠推断。
  • 228 / 583 个盒型没有结构参数。其中一类是 Pacdora 自己的手绘刀版（代码 KnifeDraw、KnifePrototype，约 50 个），在 Pacdora 那边也只是有限参数化。
  • 列表数量对不上。你截图里的 261 和 96 是 pacdora.cn 的分类计数；采集走的是 pacdora.com，折叠盒是 507 条。工作台列表不会和 .cn 页面一一对应。

4修复思路

目标不应是“把 21 个通用模板调得更像”，那条路走不通。应改成每个盒型按最可信的来源生成，并用数据说明它有多准。

① 精确参数化模板结构代码在映射表里，用 rea-* 模板，带入采集到的结构参数。可改尺寸、可调参数
→
② 编译出的结构规格由金样编译成 spec-* 模板，通过吻合度校验。可改尺寸
→
③ 尺寸锁定展示直接回放采集的刀版，与 Pacdora 完全一致，但不能改尺寸
→
④ 暂不提供以上都不满足时，只展示封面，不进入工作台

从上到下依次尝试，命中即止。通用模板（现在的做法）从这条链路里拿掉，只保留给我们自己的内置盒型。

关于第 ③ 档的授权。直接回放采集的 Pacdora 刀版坐标，项目文档里对应的阻塞项 B-GEOM-LICENSE 仍未关闭，此前的原则也是“运行时不加载第三方刀版坐标”。运输箱已经在用这种回放（src/pacdoraGeomKnife.js）。是否把它扩大到折叠盒和托盘盒、是否对外，需要你决定，见第 8 节。不启用第 ③ 档时，落到这一档的盒型归入第 ④ 档。

5分步修复方案

第 0 步：修两个显示缺陷（约 1 天）

0-A 出血线变圆

文件：src/geom/flattenPath.js。在 arcRun() 里收紧“是圆弧”的条件，三条同时满足才算：

// 1. 相邻点的转角必须小：真圆弧细分后每步转角很小，矩形的角是 90°
const MAX_STEP = Math.PI / 6            // 30°
if (steps.some(a => Math.abs(a) > MAX_STEP)) return null

// 2. 弦长必须近似相等：均匀细分的圆弧各段等长，长方形的边不等长
const chords = [];  for (let i = start; i < start + 3; i++) chords.push(dist(points[i], points[i + 1]))
const cAvg = chords.reduce((s, c) => s + c, 0) / chords.length
if (chords.some(c => Math.abs(c - cAvg) > Math.max(0.02, cAvg * 0.2))) return null

// 3. 整圈不重建：闭合环全部点都在同一个圆上时，按圆处理或保持折线，不输出单条 A 命令

更稳妥的做法是不靠事后拟合：模板生成圆弧时就在点上带圆心和半径标记，只把带标记的点列合并成弧。这是原开发方案 8.4 节的设计，当前实现走了纯拟合。本步先加上面三条保护，标记方案放到第 3 步之后。

验证：scripts/check-arcs.mjs 增加三个用例——长方形环、正方形环、正八边形面，输出中都不得出现 A 命令；圆角矩形孔仍应输出 4 段弧。

0-B 刀版缩在角落

文件：DielineCanvas.vue、useViewport.ts。

  • 用 ResizeObserver 监听画板容器；容器宽高首次大于 0 时再做第一次适应。
  • 用一个 userMoved 标记代替 scale === 1 && tx === 0：用户没有手动缩放或平移过，就在每次容器尺寸变化、切换盒型时自动适应；用户动过之后只在点“适应”时重置。
  • 适应的范围用含出血的外接范围，而不是只用面片范围。
  • 画板高度改为撑满可用高度（外层用 grid 行高 minmax(0, 1fr)），去掉固定的最小 320 像素限制。
  • fit() 里把容器内边距和左上角信息块的占位扣掉，避免刀版压在文字上。

第 1 步：把结构代码接上，启用已有的精确模板（约 2 天）

  1. 回填结构代码。scripts/backfill-structure-codes.mjs 改为按预设自带的 geomRel 找几何文件（public/{类目}-geom/{编号}.json），找不到再退回 geometry/pacdora_boxes。同时把 openParams（只取 name / value / min / max / grade）、knifeSize、outSize、面片名称签名写进预设。
  2. 去掉对 structure_inventory 的依赖。scripts/catalog-build.mjs 里 apply-structure-code-templates.mjs 改为无条件执行；该脚本本来就能从预设的 structureCode 工作。
  3. 让精确映射优先于名称关键词。构建顺序改为：结构代码精确映射 → 结构规格 → （不再有名称关键词兜底，见第 4 步）。
  4. 把结构参数带进工作台。manifestFromImportPreset()：当模板的 paramDefs 里有与采集参数同名的 code 时，把采集值作为该盒型的初始 advanced；范围取模板范围与采集的 min / max 的交集。

预期效果：53 个盒型（折叠盒 47、托盘盒 6）立刻从通用模板换成带参数的精确模板。rea-pair-ste 等模板与对应金样的吻合度已有回归脚本 scripts/check-rea-golden.mjs（面片宽高容差 1.5mm），需要把折叠盒里的同代码样本也加进这个回归。

第 2 步：为折叠盒和托盘盒编译结构规格（约 5–8 天）

这是提高覆盖面的主要手段。编译器已经存在，输入是一个金样刀版，输出是“面片树 + 尺寸表达式 + 自由边轮廓图元 + 孔图元”，运行时不含刀版坐标。

  1. 扩展输入范围。scripts/build-structure-specs.mjs 的金样目录加入折叠盒和托盘盒的几何目录；候选集合 = 有 structureCode、不在精确映射表里、不是手绘类代码的盒型。
  2. 一盒一规格。因为几乎一盒一结构，规格的键用 {结构代码}__{编号}（编译器已支持这种写法），不要指望一份规格通用于同名代码的多个盒型。
  3. 表达式拟合的依据。每个面的宽高拟合成 k × (长 | 宽 | 高 | 某结构参数) + 常数。只有一个尺寸样本时，优先匹配到结构参数（例如面宽恰好等于参数 A 的值），其次匹配长宽高的整倍数加小常数，都匹配不上则记为常数并把该盒型标为“尺寸变化不可靠”。
  4. 自动校验。沿用 scripts/validate-structure-specs.mjs，在金样尺寸下重新生成，与原刀版比较，不达标的规格剔除（标准见第 6 节）。
  5. 挂载。scripts/apply-structure-specs.mjs 按“结构代码 + 面片签名一致”接管。

预期效果不能事先保证。编译器对多件套、曲面、手绘刀版会失败。需要先跑一遍得到实际通过数，再决定剩余盒型怎么处理。建议先拿折叠盒里结构最常见的 40 个代码试跑，一天内就能知道通过率。

第 3 步：尺寸补偿按结构取值（约 1–2 天）

  • 精确模板和规格模板的 sizeRule 不再用模板级固定倍数，改为按盒型记录的加量：panelAdd = knifeSize − size、outerAdd = outSize − size（单位毫米，绑定采集时的厚度）。
  • 厚度变化时如何缩放加量，目前只有单一厚度样本，无法确定。先按“加量随厚度等比变化”处理，并在界面上保留现有的“尺寸补偿为示意值”提示。
  • 默认尺寸下，制造尺寸与 Pacdora 应完全一致，这一点可以进自动校验。

第 4 步：按吻合度分级，调整工作台列表（约 2 天）

  1. 新增脚本 scripts/check-pacdora-fidelity.mjs：对每个采集盒型，在金样尺寸下用它当前挂的模板生成刀版，与采集刀版比较，输出分数和等级，写入预设的 fidelity: { grade, score, source }。
  2. 等级与列表行为：
    等级条件工作台里怎么呈现
    A 精确来源为精确模板或规格模板，且第 6 节的指标全部达标正常可定制，高级参数可调
    B 近似拓扑一致（面片数、折线数、孔数相同），尺寸类指标略超可定制，标注“结构近似，细节可能与参考样式不同”
    L 锁定无可用模板，启用了回放（第 ③ 档）显示采集刀版，尺寸输入禁用，标注“固定规格”
    N 不提供其余列表里只显示封面，按钮为“暂不支持定制”
  3. 去掉名称关键词兜底。采集盒型不再落到 tuck-end-straight 这类通用模板上。mapTemplate() 只保留给没有几何文件的旧数据。现在挂着通用模板的约 400 个盒型，会分别进入 A、B、L 或 N。
  4. 列表改动：WorkbenchHomePage.vue 与 listWorkbenchCatalog() 增加等级徽标与筛选；默认只显示 A 和 B。

第 5 步（可选）：尺寸锁定回放（约 2 天，取决于第 8 节的决定）

  • 复用 src/pacdoraGeomKnife.js 的 loadPacdoraGeomKnife()，它已经能把采集 JSON 转成与引擎同构的 knife，含圆弧、多段切线、折叠动画，Studio 的运输箱正在用。
  • 工作台 engineClient 增加一条分支：清单 geometryMode === 'fixed_snapshot' 时走回放，尺寸、厚度、高级参数面板置为只读。
  • 导出档位只开校样稿，文件内声明与来源标注沿用运输箱的做法。

第 6 步（长期）：让“改尺寸后仍然准”可验证

现在的数据只能证明默认尺寸下像不像。要验证改尺寸后的正确性，需要同一结构在 3–5 个不同尺寸下的样本，用来检验规格里的尺寸表达式（项目此前对飞机盒就是这样做的）。这意味着追加采集，涉及对方站点的访问频率与使用条款，是否做、做多少由你决定。不做的话，A 级的含义就限定为“默认尺寸下与参考一致，尺寸变化按推断规则”。

整体目标（第 4 步完成后）：工作台列表里默认可见的采集盒型全部为 A 或 B；不再有任何采集盒型落在名称关键词挑出的通用模板上。A 和 B 各有多少个，取决于第 2 步的实际通过率，目前无法承诺具体数字。

显示缺陷的验收：任意盒型打开后，刀版在画板内居中、占画板短边的 80% 以上；调整浏览器窗口大小后仍然如此；出血线是沿切线外扩的轮廓或外接矩形，不出现圆形。

9未验证事项

  • 结构规格编译器在折叠盒和托盘盒上的通过率没有实测，第 2 步的效果是预期，不是结果。
  • “轮廓重合度”指标是建议新增的，本次没有计算；现有结论靠的是面片数、折线数、孔数、展开尺寸、线长五项。
  • 换用 rea-pair-ste 等精确模板后与金样的吻合程度，本次只确认了映射关系存在，没有逐个重算分数。
