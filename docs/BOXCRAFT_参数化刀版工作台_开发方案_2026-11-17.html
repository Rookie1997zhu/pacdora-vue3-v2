1结论摘要

BOXCRAFT 已经有了工作台需要的大部分零件：参数化引擎 src/knife.js、40 多个模板、Three.js 折叠预览、导出任务、设计稿存储和配额。缺的是一个把它们组装起来、面向客户的页面，以及引擎上几处达不到“可交付刀版”的短板。所以本方案的主体是组装和补强，不是重写。

决策 1：几何在浏览器即时算，服务端复算后才算数

Pacdora 每改一次尺寸要发约 7 个请求、等服务端出刀版。我们的引擎是纯 JS，浏览器和 Node 几何服务能跑同一份代码。预览在浏览器里做到“拖动即变”，保存和导出时由服务端用同版本引擎复算并核对 geometryHash。

决策 2：3D 继续用 Three.js 铰链树，不做 WASM

Pacdora 每次改尺寸要重新生成约 10MB 的 glTF（90 帧 morph target）。我们现有 src/render/boxModel.js 按铰链实时旋转，零传输。本期只补纸板厚度侧面、内外表面区分和分步折叠的打磨。

决策 3：一份 knife JSON 驱动全部

在现有 boxcraft.knife.v3 上做向后兼容的增量：制造尺寸模式、折线按相邻面命名、真圆弧路径、线长统计、参数分级。2D、3D、标注、报价、导出都只读这一份数据。

决策 4：复用 Design 作为“工程”，懒创建 + 自动保存

不新建工程表。登录用户第一次改参数时创建 Design（图稿图层为空），之后防抖保存。访客的状态放在 URL 和本地草稿里，登录后一键认领。

决策 5：导出走现有任务，补 AI 格式和并发上限

沿用现有导出任务与轮询，新增导出选项（标注、出血、单位、文件命名）、单组织最多 3 个进行中任务、失败重试和取消。

决策 6：首批 5 个自研模板，按工程域分档

FEFCO 0201、直插盒、翻盖邮寄盒、自锁底盒已有工程域，域内可导出工程候选稿；飞机盒先只开校样稿。fixed_snapshot 和 model_only 盒型不进工作台。Pacdora 的模板数据、WASM 和接口一律不调用、不拷贝。

< 50 ms改参数到 2D 重绘（P95，本地计算）
< 200 ms改参数到 3D 重建完成（P95）
0 请求访客预览所需的几何接口调用
≤ 20 s导出任务从提交到可下载（P95）

2目标与范围

2.1 要解决的问题

  • 客户没有入口。参数化能力目前只在 /lab（src/legacy/LegacyLab.vue，1492 行单文件）里，界面是内部调试形态；产品详情页 ProductDetailPage.vue 只有一个“填 L/W/H → 创建设计”的表单，看不到刀版就得先建稿。

3逆向结论的取舍

依据 docs/pacdora-rea/Pacdora_刀版详情页_150010_逆向报告.html 及同目录抓包样本（knife_preview.json、materials_science.json、models_details.json、permissions.json 等）。下表逐项说明 Pacdora 怎么做、我们是否照做、理由是什么。

主题Pacdora 的做法BOXCRAFT 取舍理由
几何在哪算全部在服务端；改一次尺寸约 7 个请求，每个 160–300ms部分采纳浏览器即时算，服务端复算把关我们的引擎是 JS，前后端可同构。即时反馈是可感知的体验优势。算法暴露在前端的顾虑见 16 节风险 R3
单一刀版 JSONfaces / cuts / folds / holes / bleeds / sizeArrowData / animation 一份数据驱动 2D、3D、导出采纳现有 knife v3 方向一致，补齐缺的字段即可
折线命名F_FT = F 与 FT 之间的折线；面路径的边上也标 foldline采纳2D 线、3D 铰链、导出图层用同一个名字，悬停联动和排错都简单
折叠动画数据化9 步 animations，每步若干折线同时转已有knife.foldStages + foldStages.js 已是分步数据，只需允许模板显式声明步骤
3D 生成knife2gltf.wasm 生成 glTF，预烘焙 90 个 morph target，约 10MB/次不采纳现有 Three.js 铰链树够用且零传输；WASM 是对方自有资产，不能用也没必要仿
三种尺寸类型制造 / 内 / 外，后端同时返回三套采纳引擎已算出 inner / panel / outer 三套，只缺“以制造尺寸为输入”
厚度拆分inless = ROUNDDOWN(2T/3)，outless = T − inless仅作对照我们用模板级 sizeRule（T 的倍数）。把内缩和外扩做成材质属性可以更准，但系数必须自己打样验证，不照抄
结构参数分级openParams 分 grade 2–5，每个带 min / max；高级参数要 Pro采纳结构门槛可配置paramDefs 已有 group / min / max，补 grade 和动态上下限。是否收费是商业决策（17 节 Q2）
线长统计foldlineLength / cutlineLength 随刀版返回采纳刀模按线长计价，报价模块直接可用
单位英寸只是显示层，前端换算后一律存毫米采纳与现有 lengthMm 命名一致
保存首次编辑自动建工程，之后每次改动整份 PUT，无保存按钮采纳改为防抖 + 版本号我们已有 expected_row_version 乐观锁和幂等键，比整份覆盖更安全
访客身份下发体验用户（experience_user）不采纳预览不需要服务端，访客状态放 URL 和本地即可，省掉匿名账号的清理与防刷
分享?id= 是私有工程，他人打开报 422做得更好参数写进 URL，任何人打开都能看到同一张刀版
导出服务端异步任务，2 秒轮询，最多 3 个并发，失败可重试采纳现有导出任务模式相同，补并发上限、重试、取消
缩略图前端截图后用 STS 临时凭证直传 OSS改为服务端生成服务端从 knife 直接渲染 SVG 缩略图，不需要下发存储凭证
配色切 #2028b0 / 折 #ff0000 / 出血 #68b82e保持现状我们是 #2028b0 / #fa0000 / #46ba00，同色系，不必改
营销文案“经过严格检查，可直接打印”不采纳与站点免责声明立场冲突。文案按质量档位如实标注

合规边界。本方案参考的是架构和交互模式。Pacdora 的模板坐标数据、knife2gltf.wasm、接口与素材属于对方资产，工作台运行时不调用、不内置。仓库中已有的 Pacdora 几何快照（geometry/pacdora_boxes/、public/*-geom/）只用于离线金样比对，不进入工作台的模板清单。

6总体架构

6.1 关键决策：为什么不照搬“几何全在服务端”

方案优点缺点结论
A. 全服务端（Pacdora 模式）算法不出现在前端；单一事实来源每次改动一个往返，输入有延迟；访客流量直接打到后端；离线不可用；要新建预览接口和限流不选
B. 全浏览器零延迟、零成本导出文件可被伪造的参数或被改过的前端代码影响；无法审计不选
C. 同构：浏览器预览 + 服务端复算体验最好；导出可信；访客不耗后端；现有代码已接近这个形态必须保证两端引擎版本一致；算法在前端可见采用

方案 C 的两个代价都有对策：版本一致靠 engineVersion + geometryHash 双重校验（10.3 节）；算法可见的问题通过“可生产级模板可标记为 serverOnly”保留退路——这类模板的浏览器端只拿到服务端返回的 knife，不下发生成函数（9.3 节）。首批模板不启用 serverOnly。

8.1 制造尺寸模式 P0

现状：deriveSizes() 把输入当作内尺寸或外尺寸，再推出 panel。新增第三种入口，把输入当作 panel：

8.4 真圆弧路径 P1

目标：圆角孔和倒角在 PDF / SVG / DXF 中是真正的弧，而不是 4–10 段折线。分两步走，避免动到并集与偏移算法：

  1. 弧标记透传。模板产生圆弧的地方（holeLoop、taperRoundFlap 等）在细分点上附带 arc: { cx, cy, r, id } 元数据。并集和去重步骤保留该元数据。
  2. 弧重建。生成 paths 时，把连续且 arc.id 相同、端点仍在圆上的点列合并回一条 A 命令；被布尔运算切断的弧按剩余部分重建；无法确认的保持折线。内部计算（并集、出血偏移、碰撞）继续用折线，细分精度提高到弦高 ≤ 0.05mm。

出血线的弧：偏移后的圆角半径为 r + bleed，同法重建。自锁底模板已有的精确三次贝塞尔（src/crashlock/）直接映射为 C 命令。

8.5 出血语义 P1

  • createKnife({ bleed, previewBleedExtra = 0 })：工作台与导出传 0；LAB 和 Studio 为保持现有观感继续传 10。
  • 画板上出血线离切线太近（屏幕距离 < 3px）时，靠线宽和颜色区分，不靠改几何。

9.4 2D 画板

  • 用 SVG，不用 Canvas / Konva。刀版线条数量在数百条量级，SVG 足够；矢量缩放不糊；可直接复用于缩略图和导出预览；便于无障碍和测试。Konva 继续只用于 Studio 的图稿编辑。
  • 结构。<svg> → <g transform=视口> → 各图层 <g>。缩放平移只改外层 transform。线条使用 vector-effect: non-scaling-stroke，线宽不随缩放变化。
  • 路径合并。每个图层的同类线合并成一条 <path>（切线一条、折线一条、出血一条）；面片各自一个 <path>，用于悬停命中和填充。
  • 标注。buildDimAnnotations(knife) 的结果渲染到 DimLayer；文字大小按屏幕像素固定（反向缩放）；数值经 useUnit 格式化。
  • 视口。初次和切换模板时自适应留白 8%；改参数时保持缩放比例，仅当刀版超出可视区时才重新适应，避免每次输入画面跳动。
  • 配色。沿用 #2028b0 切线、#fa0000 折线（虚线）、#46ba00 出血。线型同时用实线和虚线区分，不只靠颜色。

9.5 3D 预览

  • 直接使用 createKnifeScene(container, { materialId, onPanelSelect })，与 Studio 的 StudioFoldPreview.vue 同一套 API：setKnife / setProgress / setSelectedPanel / resetView / dispose。

  • 进度。滑块 0–100 → setProgress(p / 100)；步骤文字用 stageIndexAt()。默认停在 100（合盖）并带轻微俯角。

9.6 单位与数值

Revision 合并规则

DesignRevision 增加字段 kind：checkpoint（默认，现有行为）或 autosave。收到 autosave: true 的保存请求时，若同时满足以下条件，则原地更新当前头部 Revision，不新建：

  1. 头部 Revision 的 kind 是 autosave，且创建者是当前用户；
  2. 创建时间在 10 分钟以内；
  3. 没有被 ExportJob.input_revision、Quote.design_revision、订单项或渲染场景引用。

否则新建一条 autosave Revision。原地更新同样要比对并递增 row_version，同样记录幂等键。被导出或报价引用过的 Revision 永不修改，可追溯性不受影响。响应里的 coalesced: true 仅用于调试与统计。

为什么不直接放宽成“每次都新建”。一次调参会话常有几十次改动；每次保存还要同步调用一次几何服务。合并后，一次会话通常只留下 1–3 条 Revision，几何服务的调用量也由 3 秒防抖控制在可接受范围。

访客认领

访客点“保存”或“下载”→ 跳登录页并带 next=/workbench/:slug?…当前参数…&claim=1 → 登录或注册回来后，前端发现 claim=1 且已登录，立即走懒创建。全程不需要服务端保存匿名数据。

10.5 浏览器与服务端一致性

  1. 前端保存时附带 client_geometry_hash（Worker 算出的 g1: hash）。
  2. 服务端 apply_server_geometry 照旧调用 /validate 得到权威 hash 并入库。
  3. 两者不同：保存仍然成功（以服务端为准），响应 geometry_drift: true，并写一条结构化日志（模板、版本、参数、两个 hash）。前端显示“预览与服务端结果不一致，请刷新页面”，并禁用导出直到刷新。
  4. 导出永远基于服务端重算的几何，前端传来的 knife 不参与导出。

漂移率是上线后的核心健康指标，目标为 0；任何一次漂移都按缺陷处理。
